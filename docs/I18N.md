# Internationalization Guide — CRM AI Engine

## Overview

The dashboard supports English (default) and Arabic with full RTL layout.

## Architecture

```
backend/core/i18n.py         ← Translation loader + helpers
frontend/translations/
├── en.json                  ← English strings (source of truth)
└── ar.json                  ← Arabic translations
```

## How it works

1. On server startup, `load_translations()` reads all JSON files from `frontend/translations/`
2. Each route handler calls `detect_lang(cookies, accept_language)` to identify the user's language
3. A `make_translator(lang)` bound function is passed to every template as `_t`
4. Templates call `{{ _t("Key String") }}` for any user-visible text

## Adding a new language

1. Create `frontend/translations/<code>.json` (e.g., `fr.json`)
2. Add `"fr"` to `SUPPORTED_LANGS` in `backend/core/i18n.py`
3. Copy all keys from `en.json` and translate the values
4. Add a flag button in the topbar dropdown in `base.html`

## Translation file format

```json
{
  "Dashboard": "لوحة التحكم",
  "Total Leads": "إجمالي الفرص",
  ...
}
```

Keys are the English display strings. Values are the translations.

## Language detection order

1. `lang` cookie (set by JS `document.cookie = 'lang=ar;path=/'`)
2. `Accept-Language` HTTP header (checks for `ar`)
3. Default: `en`

## RTL layout

When `lang=ar`:
- `dir="rtl"` is set on `<html>` server-side (no flash)
- Tailwind `rtl:` variants handle flips: `rtl:rotate-180` for arrows, `rtl:left-4` for positioned elements
- Chart legends reflow naturally with the browser's RTL rendering

## Template usage

```html
<!-- In Jinja2 templates -->
{{ _t("Total Leads") }}

<!-- With fallback (key returned if no translation found) -->
{{ _t("Some New Key") }}  →  "Some New Key" (EN fallback)
```

## JS language switching

```js
// In app.js / Alpine.js
setLang('ar');   // sets cookie, reloads page
setLang('en');   // sets cookie, reloads page
```

The page reload triggers a new server-side render with the correct language context.

## Key naming conventions

Two patterns are both valid and in use:

| Pattern | When to use | Example |
|---------|-------------|---------|
| **Self-keyed** (English = key) | Short strings where the English text is self-documenting | `"Running"`, `"Headcount"`, `"Departments"` |
| **Machine key** (`module_description`) | Long strings, parameterized text, JS-only strings, or strings that need copy improvements over the raw English | `"hr_aggregate_wage_only"`, `"hr_err_session"`, `"ai_priority_queue"` |

Every machine key MUST appear in both `en.json` (with its English value) and `ar.json` (with the Arabic translation). If the Arabic is missing, the key itself is shown as fallback — which is always worse than English for Arabic users.

## JS string injection pattern (window.*_STRINGS)

JS controllers cannot call `_t()` at runtime. Instead, a module's page template injects a locale-resolved strings object via a `<script>` block, and the JS reads from it with an `_s(key, fallback)` helper.

```html
<!-- In the module's dashboard template, inside {% block extra_scripts %} -->
<script>
window.HR_STRINGS = {
  running: "{{ _t('Running') | e }}",
  err_session: "{{ _t('hr_err_session') | e }}",
  months: ["{{ _t('hr_month_jan') | e }}", ...]
};
</script>
```

```js
// In the JS controller
var S = window.HR_STRINGS || {};
function _s(key, fallback) { return (S[key] != null) ? S[key] : fallback; }

// Usage
_showError(_s('err_session', 'Session expired — please refresh the page.'));
```

The English fallback in every `_s()` call ensures the panel works if the script block somehow fails. Coverage checker skips `|| 'fallback'` positions — they are not bare strings, they are robustness guards.

Precedent: `window.CHAT_STRINGS` in `base.html` (CRM/chat module). `window.HR_STRINGS` in `hr/dashboard.html` (HR module).

## HR-specific notes

- **Wage display**: `hr.contract.wage` is the monthly base wage; allowances are separate fields excluded from Phase 1 displays. Arabic label "إجمالي الراتب الأساسي فقط" correctly uses "الأساسي".
- **Contract dates**: Neutral phrasing — "حتى {date}" (through), "غير محدد المدة" (open-ended). No urgency language.
- **Digits**: Western (0–9) throughout. Arabic month names used for F3 formatted dates; surrounding digits stay Western.
- **RTL**: `rtl:rotate-180` (chevron flip) and `rtl:text-left` (amount column) are the first `rtl:` variant classes in this project (Tailwind 3.4.19 built-in support).
- **Pluralization**: 2-form approximation (n=1 singular, n≠1 plural). Known v1 limitation.
- See `docs/HR_IMPLEMENTATION_DECISIONS.md` for full decision log.
